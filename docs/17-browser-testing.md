# StreamFlix browser testing through ingress

The browser test console at `/lab` exercises the deployed application through ingress. It has forms and buttons for registration, login, profiles, notes, search, recommendations, notifications, simulated billing, catalog viewing events, and the admin Pod list. Responses show the HTTP status and returned data.

## Deploy the browser console

Run these commands manually from the project directory. The new image tag avoids reusing a cached `v1` image. If `browser-v2` has already been published, choose another unused tag.

```bash
cd /mnt/c/Users/sandeep.reddy01/Downloads/k8s-project
docker build -t docker.io/sandeep030701/frontend:browser-v2 app/frontend
docker push docker.io/sandeep030701/frontend:browser-v2
helm upgrade --install frontend gitops/charts/frontend -n streamflix \
  --set image.tag=browser-v2
kubectl rollout status deployment/frontend -n streamflix --timeout=180s
kubectl apply -f gitops/infra-manifests/observability/grafana-ingress.yaml
```

After successful validation, set `image.tag: browser-v2` in the frontend `values.yaml` to preserve the chosen image for subsequent upgrades. The commands do not commit or push Git changes. GitOps automation is still a separate project phase.

## Open the application and Grafana

Ensure the Windows hosts file contains these entries:

```text
127.0.0.1 streamflix.local
127.0.0.1 grafana.streamflix.local
```

Keep one terminal running:

```bash
kubectl port-forward -n ingress-nginx svc/ingress-nginx-controller 8080:80
```

Open:

- Application test console: `http://streamflix.local:8080/lab`
- Grafana: `http://grafana.streamflix.local:8080`
- Raw catalog JSON: `http://streamflix.local:8080/api/catalog/titles`
- Raw Pod list: `http://streamflix.local:8080/pods`

The tunnel reaches the ingress controller; nginx still selects the host and path and forwards each request to the corresponding Service. Both hosts share that single tunnel.

## Ingress routes

| Host and path | Backend |
| --- | --- |
| streamflix.local, `/` including `/lab` | frontend:8080 |
| streamflix.local, `/api` prefix | api-gateway:8080 |
| streamflix.local, exact `/pods` | admin-dashboard:8080 |
| grafana.streamflix.local, `/` | kube-prometheus-stack-grafana:80 in observability |

The application routes are in the frontend Helm chart. The Grafana Ingress is a separate manifest in observability because its Service is in that namespace. Gateway requests keep their `/api/...` path; the application gateway handles service routing. No ingress path rewriting is needed.

## Browser test sequence

1. Click **Load catalog**. Expect movie cards and HTTP 200. Check a movie's view count, click **Record view**, wait a few seconds, then check its count again. An increment establishes event delivery through Kafka, activity-tracker, and Redis. `eventPublished: true` alone does not establish delivery.
2. Click **Register**, then **Log in**, using the generated test email and a lab password. Expect HTTP 201 then 200. The token is hidden in the result. The other endpoints do not enforce login.
3. Save a profile, then read it. Verify the display name matches. Saving a note exercises the user volume write; the application has no note read endpoint, so volume persistence needs a separate check.
4. Search for **Cluster**. Expect the seeded Elasticsearch title. The index is seeded independently from the Postgres catalog.
5. Request recommendations twice within 60 seconds. The second response should come from cache. The service can use fallback titles when catalog is unavailable; inspect catalog metrics to establish its participation.
6. Queue a notification and read notifications. Expect the stored message. This lab does not deliver real emails.
7. Run a simulated charge and check `provider_key_loaded`. No real payment occurs.
8. List application Pods. Expect the admin service to return Pod data using its Kubernetes ServiceAccount.
9. Open Grafana and inspect metrics and logs generated by these actions. ServiceMonitors must be selected by Prometheus, and collectors must deliver logs to Loki. Application traces require OpenTelemetry instrumentation, which remains pending.

Jobs, volume durability, HPA/VPA behavior, policy enforcement, TLS, and CI/CD rollouts require their own verification. A successful browser response does not establish those platform capabilities.
